# Claude Code로 프레젠테이션 만들기 - 실전 방법론

**작성일**: 2025-01-20
**목적**: Claude Code를 활용한 프레젠테이션 제작 방법론 공유
**대상**: 동료 개발자, Claude Code 사용자

---

## 🎯 이 문서의 목적

이 문서는 **"Claude Code로 어떻게 프레젠테이션을 만드는가"**에 대한 실전 가이드입니다.
특정 프레젠테이션의 내용보다는, **작업 방식과 협업 패턴**에 초점을 맞춥니다.

### 핵심 질문
- 어떻게 요청해야 효과적인가?
- 어떤 도구를 언제 사용하는가?
- 피드백은 어떻게 주는가?
- 어떻게 반복해서 개선하는가?

---

## 📐 전체 작업 흐름

```
1. 초기 탐색 (Exploration)
   └─ MCP 도구로 리소스 수집

2. 구조 설계 (Structure)
   └─ 대화로 목차 확정

3. 내용 작성 (Content)
   └─ 섹션별 스크립트 작성

4. 시각화 (Visualization)
   └─ HTML/CSS로 슬라이드 구현

5. 개선 (Refinement)
   └─ 피드백 반영 및 반복
```

---

## 💡 핵심 인사이트: 계층적 접근

### ❌ 실패하는 접근: 슬라이드부터 시작
```
"홀덤 소개 프레젠테이션 만들어줘"
→ Claude가 슬라이드 디자인부터 고민
→ 내용이 얕고 메시지가 불명확
```

### ✅ 성공하는 접근: 책 목차부터 시작
```
1. 책 목차 작성 (논리적 흐름)
   ↓
2. 발표 스크립트 (자연스럽게 풀어쓰기)
   ↓
3. 슬라이드 (시각적 보조)
```

**이유**: 좋은 책은 소리 내어 읽어도 자연스럽다. 좋은 발표도 마찬가지.

## 🛠️ 작업 패턴별 가이드

### 패턴 1: 리소스 수집 (MCP 활용)

#### 상황
외부 자료(블로그, 논문, 뉴스)를 프레젠테이션에 통합하고 싶을 때

#### 사용자 요청 방식
```
❌ 막연함: "홀덤 관련 자료 찾아줘"
✅ 구체적: "이 블로그 글을 읽고 핵심 주제 3가지를 추출해줘"
```

#### Claude가 사용한 도구
- **Chrome DevTools MCP**: 웹 페이지 읽기 및 스크린샷
- **WebFetch**: URL에서 콘텐츠 추출 및 요약

#### 실제 작업 사례
```
사용자: "https://blog.naver.com/... 이 글 요약해줘"
Claude:
  1. WebFetch로 페이지 내용 추출
  2. 핵심 주제 분석 (불확실성, +EV 개념)
  3. sources/naver_blog_summary.md에 저장
  4. 발표에서 활용 가능한 인용구 정리
```

#### 효과적인 협업 팁
- **URL을 직접 제공**: "이런 내용 찾아줘" < "이 링크 분석해줘"
- **저장 위치 지정**: `sources/` 디렉토리에 정리 요청
- **활용 목적 명시**: "발표에서 인용할 예정" → Claude가 형식 맞춤

---

### 패턴 2: 구조 설계 (대화를 통한 목차 확정)

#### 상황
프레젠테이션의 흐름과 논리를 잡아야 할 때

#### 사용자 요청 방식
```
❌ 한 번에 완성 요구: "완벽한 목차 만들어줘"
✅ 점진적 개선: "이 순서가 맞나?" → 피드백 → 수정 반복
```

#### 실제 대화 흐름
```
[1차] Claude: 초안 제시 (시나리오 → 게임 설명)
[피드백] 사용자: "게임 설명 먼저, 시나리오 나중에"
[2차] Claude: 구조 변경 (게임 설명 → 시나리오)
[피드백] 사용자: "+EV 개념 추가해줘"
[3차] Claude: 섹션 추가 및 재배치
```

#### 핵심 원칙
- **완벽주의 피하기**: 초안은 빠르게, 피드백으로 개선
- **"왜"를 설명하기**: "순서 바꿔줘" < "초보자가 이해하려면 기본 설명이 먼저 필요해"
- **점진적 명확화**: 막연한 아이디어 → 대화로 구체화

---

### 패턴 3: 내용 작성 (Read → Edit 사이클)

#### 상황
기존 문서를 수정하거나 내용을 추가할 때

#### Claude 작업 방식
1. **Read**: 현재 파일 읽기 (전체 또는 특정 라인)
2. **Edit**: 정확한 old_string → new_string 교체
3. **확인**: 변경사항 출력으로 확인

#### 효과적인 수정 요청
```
❌ 모호함: "Act 4 고쳐줘"
✅ 구체적: "Act 4를 '의사결정 도구'로 프레이밍해줘.
           웹툰 인용 추가하고, 인생과 비교하는 표 넣어줘"
```

#### 실제 작업 사례
```
사용자: "Act 4를 감성적으로 바꾸고 싶어.
        블로그에서 정리한 긴 인용문 넣어줘"

Claude:
  1. Read outline.md (Act 4 부분)
  2. Read sources/naver_blog_summary.md (인용문 확인)
  3. Edit outline.md (Act 4 전체 재작성)
     - 인용문 추가
     - 청년 세대 연결
     - 감성적 메시지 강화
```

---

### 패턴 4: 병렬 작업 vs 순차 작업

#### 병렬 작업이 효과적인 경우
```
✅ 독립적인 리소스 수집
   예: 블로그 A, 논문 B 동시에 요약

✅ 여러 파일 동시 읽기
   예: outline.md, sources/*.md 함께 분석
```

#### 순차 작업이 필요한 경우
```
✅ 의존성이 있는 작업
   예: 파일 읽기 → 내용 기반 수정

✅ 사용자 피드백이 필요한 경우
   예: 초안 제시 → 승인 → 다음 단계
```

#### 사용자 요청 팁
```
병렬 원할 때: "이 3개 링크 동시에 분석해줘"
순차 원할 때: "이거 확인하고 다음 단계 물어봐"
```

### 패턴 5: 컴포넌트 기반 설계 (재사용 가능한 요소)

#### 상황
프레젠테이션에 필요한 시각 자료를 만들 때

#### 잘못된 접근 vs 올바른 접근
```
❌ 잘못된 접근: 완성된 슬라이드 이미지 생성
   예: "GTO vs Exploit 비교 슬라이드 만들어줘"
   → 한 번 쓰고 버리는 이미지, 재사용 불가

✅ 올바른 접근: 작은 재사용 가능한 요소들 생성
   예: "칩 아이콘, 액션 뱃지, 비교 템플릿 같은 조립 가능한 요소들"
   → 다양한 슬라이드에서 조합해서 사용 가능
```

#### 실제 피봇 사례
```
[1차 시도] Claude: GTO vs Exploit 전략 비교 슬라이드 생성
           (완성된 이미지 1개)

[피드백] 사용자: "presentation page 1개를 그려주는구나.
                 그건 여기 역할이 아니야."

[이해] Claude:
  - 완성된 슬라이드가 아니라 "레고 블록" 같은 요소들 필요
  - 다양하게 조합 가능한 작은 컴포넌트
  - 예: 칩, 카드, 화살표, 뱃지, 아이콘 등

[2차 접근] Claude: 25개의 재사용 가능한 SVG 요소 생성
  - 게임 구성 요소: chip-stack, pot-icon, dealer-button
  - 액션 뱃지: FOLD, CALL, RAISE
  - 인디케이터: checkmark, x-mark, warning, +EV
  - 비교 템플릿: vs-divider, comparison-table
  - 전략 시각화: position-diagram, gto-exploit-icon

[결과] 사용자: "맞아 그런걸 만들고 어디에 쓰면 좋을지
               README나 어딘가에 쓰면 좋을 듯"
```

#### 작업 방식
```
1. 카테고리별 분류
   elements/
   ├── chips/          (게임 구성 요소)
   ├── actions/        (액션 뱃지)
   ├── indicators/     (상태 표시)
   ├── templates/      (레이아웃 템플릿)
   └── visualizations/ (전략 시각화)

2. 병렬 파일 생성
   - 각 SVG는 독립적 → Write 도구로 동시에 여러 개 생성
   - 일관된 디자인 패턴 (컬러, 필터, 크기)

3. 사용 가이드 문서화
   - DIAGRAM-ELEMENTS.md 생성
   - 각 요소의 목적, 사용법, HTML 예시
   - 조합 패턴 제시
```

#### 효과적인 요청 방식
```
❌ "홀덤 프레젠테이션 이미지 만들어줘"
   → 너무 막연함, 완성된 슬라이드로 오해

✅ "칩, 카드, 액션 뱃지처럼 조합 가능한 SVG 요소들 만들어줘.
    레고 블록처럼 여러 슬라이드에서 재사용할 수 있게"
   → 명확한 의도, 재사용성 강조
```

#### 핵심 원칙
- **조립 가능성**: 작은 요소들을 조합해서 다양한 표현
- **일관성**: 컬러 스킴, 스타일, 크기 통일
- **문서화**: 어떻게 사용하는지 가이드 제공
- **효율성**: 한 번 만들면 여러 곳에서 재사용

#### 다른 프로젝트 적용
```
기술 문서 → 아이콘 라이브러리
교육 자료 → 다이어그램 컴포넌트
대시보드 → 차트 요소
마케팅 → 인포그래픽 조각들
```

### 패턴 6: 세션 연속성 관리 (Long-running Projects)

#### 상황
프로젝트가 길어져서 대화 컨텍스트가 부족할 때

#### 문제
Claude Code는 컨텍스트 윈도우(메모리) 제한이 있습니다:
- 긴 대화가 계속되면 컨텍스트가 꽉 참
- 예: 이미지 생성, 문서 작성, 피드백, 수정... 반복하다 보면 200K 토큰 도달

#### Claude의 자동 처리
```
[컨텍스트 부족 감지]
→ Claude가 자동으로 대화 요약 (conversation summary) 생성
→ 새 세션 시작하면서 요약을 전달
→ 작업 맥락을 유지한 채 계속 진행
```

#### 실제 사례: 홀덤 프레젠테이션 프로젝트
```
[세션 1 - ASIS (As-Is)]
1. YouTube 스크린샷 캡처
2. 웹툰 인용구 SVG 생성
3. 52개 카드 SVG 생성 (스크립트 자동화)
4. Hand rankings 차트 생성 및 수정
5. Diagram elements 25개 생성 시작
   → 컨텍스트 한계 도달 (약 180K 토큰)

[자동 전환]
Claude가 전체 대화를 요약:
- Primary Request: 홀덤 프레젠테이션 이미지 생성
- Key Concepts: 재사용 가능한 SVG 컴포넌트
- Errors and Fixes: "hand-rankings" 오해 수정
- Pending Tasks: Diagram elements 완료, 가이드 작성

[세션 2 - TO-BE (새 세션)]
요약과 함께 시작:
"This session is being continued from a previous conversation..."
→ 바로 diagram elements 작업 계속
→ DIAGRAM-ELEMENTS.md 작성 완료
→ Development log 업데이트 진행 중
```

#### 세션 전환 시 장점
```
✅ 자동: 사용자가 신경 쓸 필요 없음
✅ 매끄러움: 작업 맥락 유지
✅ 요약: 핵심만 남겨서 더 집중된 작업
✅ 신속함: 이전 실수 반복 안 함
```

#### 사용자가 할 수 있는 일
```
1. 중간 체크포인트 만들기
   "지금까지 작업 상태를 README에 정리해줘"
   → 세션 끊겨도 쉽게 복구

2. 파일로 맥락 유지
   - outline.md (프로젝트 구조)
   - CLAUDE.md (작업 원칙)
   - development-log/ (진행 상황)
   → 파일 읽기만 해도 프로젝트 이해

3. 명확한 다음 단계 명시
   "다음에는 X를 해야 해"
   → 요약에 포함되어 새 세션에서 이어짐
```

#### 피해야 할 것
```
❌ 구두로만 중요 정보 전달
   예: "이거 중요한데 기억해줘"
   → 요약에서 누락될 수 있음

✅ 파일에 기록
   예: "이 중요한 결정을 DECISIONS.md에 저장해줘"
   → 영구 보존, 언제든 참조 가능
```

#### 긴 프로젝트 작업 패턴
```
Day 1: 프로젝트 셋업, 구조 설계
  → CLAUDE.md, outline.md 생성

Day 2-3: 핵심 기능 구현
  → 중간중간 README 업데이트

Day 4: 컨텍스트 한계 → 자동 세션 전환
  → 파일 읽기로 맥락 회복 → 작업 계속

Day 5: 완성 및 문서화
  → development-log 작성
```

#### 핵심 교훈
> **"파일은 영원하고, 대화는 일시적이다"**

중요한 결정, 작업 방향, 핵심 원칙은 반드시 파일에 기록.
Claude가 세션이 바뀌어도 파일을 읽고 맥락을 이해할 수 있게.

### 패턴 7: 초기 방향 설정 (Cold Start Problem)

#### 문제 상황
프로젝트를 처음 시작할 때, 정확히 어떤 방향으로 갈지 모르는 상태

#### 선택지들

**옵션 A: 빠른 프로토타입**
- 어떻게: 작은 샘플을 빠르게 만들어 방향 확인
- 장점: 빠름, 구체적으로 볼 수 있음
- 단점: 버려질 수 있음 (시간 낭비 가능)
- 언제: 시간 여유 있고, 시각적 확인 필요할 때

**옵션 B: 갈림길 질문**
- 어떻게: Claude가 "A 스타일? B 스타일?" 질문
- 장점: 빠른 방향 결정
- 단점: 사용자가 선택지를 이해해야 함
- 언제: 명확한 두 가지 옵션이 있을 때

**옵션 C: 점진적 명확화 (발견적)**
- 어떻게: 일단 시작 → 피드백 → 방향 조정
- 장점: 유연함, 작업하며 배움
- 단점: 초기 결과물 버려질 수 있음
- 언제: 불확실성이 크고, 탐색이 필요할 때

#### 선택 시 고려사항

```
프로젝트 불확실성:
- 낮음 (명확) → A 또는 B
- 높음 (모호) → C

시간 제약:
- 급함 → B (빠른 결정)
- 여유 → A 또는 C

사용자 경험:
- 이 분야 잘 앎 → B
- 처음 접함 → C
```

#### 이 프로젝트에서는

우리는 **C (점진적 명확화)**를 선택했다.

**이유:**
- 프레젠테이션 정확한 스타일 몰랐음
- "슬라이드 기반 vs 스크립트 기반" 개념조차 없었음
- 탐색하며 방향 찾는 게 필요

**결과:**
- 좋았던 점: "책 목차 → 스크립트 → 슬라이드" 발견
- 아쉬웠던 점: 초기 슬라이드 중심 작업 버려짐 (시간 낭비)
- 개선: 다음엔 B (갈림길 질문)로 30% 시간 절약 가능

**핵심 교훈:**
> "첫 프로젝트는 필연적 시행착오.
> 중요한 건 그걸 문서화(CLAUDE.md)해서
> 두 번째부턴 B로 빠르게 시작"

### 패턴 8: 피드백과 검증

#### 문제 상황
작업 결과가 요구사항에 맞는지 확인하고, 수정이 필요한지 판단해야 할 때

#### 선택지들

**옵션 A: 사용자 피드백 의존**
- 어떻게: 결과 → 사용자 확인 → 피드백 → 수정
- 장점: 정확함 (사용자가 최종 판단)
- 단점: 사용자 부담 큼, 피드백 스트레스
- 언제: 작은 프로젝트, 빠른 반복 가능

**옵션 B: 체크리스트 검증**
- 어떻게: 사전 정의된 체크리스트로 자체 점검
- 장점: 명확한 기준, 객관적
- 단점: 체크리스트 작성 필요
- 언제: 요구사항이 명확한 프로젝트

**옵션 C: Self-Review (Claude 자가 검증)**
- 어떻게: 작업 완료 → Claude가 스스로 점검 → 문제 발견 시 수정 → 최종본 제출
- 장점: 사용자 부담 감소 (70-80% 걸러냄)
- 단점: 100% 완벽 불가능, 명시적 기준 필요
- 언제: 반복적 작업, 명확한 원칙 있을 때

**옵션 D: Two-Pass 방식**
- 어떻게: 1차 초안 → 자체 리뷰 → 2차 수정 → 사용자 제출
- 장점: A와 C의 균형
- 단점: 시간 조금 더 걸림
- 언제: 퀄리티 중요, 사용자 피드백 최소화 원할 때

#### 선택 시 고려사항

```
사용자 가용 시간:
- 많음 → A (직접 피드백)
- 적음 → C 또는 D

작업 반복성:
- 한 번 → A
- 여러 번 → C (자동화)

기준 명확도:
- 불명확 → A (사용자 판단)
- 명확 → B, C (자동 검증)
```

#### 이 프로젝트에서는

**초기: A (사용자 피드백)**
- "중앙에 큰 텍스트 이거 진짜 개구리다"
- → 전면 재작성

**이후: 암묵적 C (Self-Review)**
- CLAUDE.md의 원칙 참조
- "슬라이드 중심 표현 있나?" 자체 점검

**결과:**
- A → C 전환으로 피드백 횟수 감소
- 하지만 100% 자동화는 불가능
- 적절한 균형: 명시적 체크리스트(B) + Self-Review(C)

**개선 제안:**
```
작업 요청 시:
"outline.md 작성해줘.

체크리스트로 자체 검증:
- [ ] '화면에', '슬라이드' 단어 없음
- [ ] 책 목차처럼 읽힘
- [ ] 소리 내어 읽으면 자연스러움

통과하면 제출, 안 되면 수정 후 제출"
```

### 패턴 9: 파일 간 일관성 유지

#### 문제 상황
설계 파일(outline.md)이 바뀌면 구현 파일(scripts/)도 바뀌어야 하는데, 어떻게 관리할까?

#### 선택지들

**옵션 A: 구두 Sync 요청**
- 어떻게: "outline 바꿨으니 scripts도 맞춰줘"
- 장점: 간단, 빠름, 관리 부담 없음
- 단점: 까먹을 수 있음
- 언제: 작은 프로젝트 (파일 <10), 혼자 작업

**옵션 B: 간단한 메모**
- 어떻게: README나 CLAUDE.md에 "outline 바뀌면 scripts 체크"
- 장점: 기록 남음, 부담 적당
- 단점: 형식 없어서 불명확
- 언제: 중간 프로젝트 (파일 10-30)

**옵션 C: 의존성 문서 (PROJECT-STRUCTURE.md)**
- 어떻게: 파일 계층, 의존 관계, 변경 영향 체크리스트 문서화
- 장점: 명확함, 팀 협업 쉬움, 확장 가능
- 단점: 유지보수 부담, 시간 많이 걸림
- 언제: 큰 프로젝트 (파일 30+), 팀 작업

**옵션 D: 주기적 일관성 체크**
- 어떻게: "전체 파일 일관성 체크해줘" (세션 시작 시)
- 장점: 놓친 것 발견
- 단점: 매번 체크 필요
- 언제: 장기 프로젝트, 여러 세션 걸쳐 작업

#### 선택 시 고려사항

```
프로젝트 크기:
- 파일 <10 → A
- 파일 10-30 → B
- 파일 30+ → C

팀 규모:
- 혼자 → A 또는 B
- 2-3명 → B
- 팀 → C

프로젝트 기간:
- 1-2주 → A
- 1-2달 → B
- 장기 → C

미래 확장성:
- 필요 없음 → A
- 가능성 있음 → B
- 확실함 → C
```

#### 이 프로젝트에서는

우리는 **A (구두 sync)**를 선택했다.

**이유:**
- 파일 적음 (outline, scripts, images 정도)
- 혼자 작업
- 1-2주 프로젝트
- 팀 확장 계획 없음

**실제 사례:**
```
문제:
- outline Act 4 변경
- scripts만 수정
- 하지만 outline이 근본 원인

해결:
사용자: "outline 바꿨으니 scripts도 sync 해줘"
→ 간단하고 효과적
```

**결과:**
- A로 충분했음
- C (의존성 문서)는 과잉이었을 것

**⚠️ 주의:**
> "작은 프로젝트에 큰 관리 체계 = 과잉 엔지니어링
> 프로젝트 크기에 맞게"

### 패턴 10: 세션 관리 및 Lock 시스템 (다중 세션 협업)

#### 문제 상황

여러 Claude 세션이 동시에 작업할 때:
- **세션 정체성**: 세션 재시작 시 "나는 누구?" 모름
- **Git conflict**: 같은 파일을 여러 세션이 수정
- **작업 순서**: 의존성 관리 필요 (Act 2 완료 → Act 3 시작)
- **조율 부담**: 사용자가 매번 "너는 Session X" 지정

#### 선택지들

**옵션 A: CLAUDE.md에 Current Sessions 섹션**
- 어떻게: CLAUDE.md에 각 세션의 Identity, Tasks 기록
- 장점: 간단, 한 파일에 모든 정보
- 단점: 세션별 상세 정보 부족, CLAUDE.md가 혼잡해짐
- 언제: 2-3개 세션, 단순한 작업

**옵션 B: 세션별 작업 파일 (.claude/sessions/)**
- 어떻게: session1.md, session2.md 등으로 분리
- 장점: 세션마다 독립적 파일, 명확한 분리
- 단점: 파일 많아짐, 전체 조율 어려움
- 언제: 많은 세션 (5개 이상), 장기 프로젝트

**옵션 C: Lock 시스템 (SESSION-LOCK.md)** ⭐ 선택
- 어떻게: 중앙 lock 파일 + 작업별 가이드 문서
- 장점:
  - 세션 정체성 + 작업 내용 + Lock 관리 통합
  - Task Queue로 의존성 명확
  - Conflict 사전 방지
  - 작업 상태 실시간 파악
- 단점: 초기 설정 필요, 규칙 준수 필요
- 언제: 3-5개 세션, 의존성 있는 작업, conflict 가능성 높음

#### 선택 시 고려사항

```
세션 수:
- 1-2개 → A 또는 관리 불필요
- 3-5개 → C (Lock 시스템)
- 5개+ → B (세션별 파일)

작업 의존성:
- 독립적 → A
- 순서 있음 → C
- 복잡한 DAG → B + 워크플로우 도구

Conflict 가능성:
- 다른 파일 → A
- 같은 파일 다른 섹션 → C
- 같은 파일 자주 충돌 → B + Git branch 전략

프로젝트 기간:
- 단기 (1-2주) → A
- 중기 (1-2달) → C
- 장기 (3달+) → B
```

#### 이 프로젝트에서는

우리는 **C (SESSION-LOCK.md + 작업 가이드)**를 선택했다.

**이유:**
- 3개 세션 (Session 1: Act 2, Session 2: 방법론, Session 3: Act 3)
- 작업 의존성 있음 (Act 2 → Act 3)
- 같은 파일(index.html) 다른 섹션 수정
- Conflict 방지 필요

**구조:**
```
SESSION-LOCK.md           (세션 관리 허브)
  ├─ Session 1: Act 2    → ACT2-FEEDBACK-AND-GUIDE.md
  ├─ Session 2: 방법론    → (완료)
  └─ Session 3: Act 3    → (대기 중)

index.html Act 2 섹션
  └─ 주석: "⚠️ LOCKED by Session 1"

development-log/CLAUDE.md
  └─ "다음 작업" 최우선 항목 표시
```

**SESSION-LOCK.md 내용:**
- **Active Sessions**: 각 세션의 Status, Identity, Locked Resources, Tasks
- **Task Queue**: Ready, Waiting, Backlog
- **Rules**: 작업 시작/중/완료 시 워크플로우

**작업 가이드 문서 (ACT2-FEEDBACK-AND-GUIDE.md):**
- 빠른 참조 (현재 상태 요약)
- 구체적 개선 방안 (Option A/B)
- 슬라이드별 상세 스펙 (HTML 예시)
- 작업 체크리스트
- 주의사항

**워크플로우:**
```
1. 세션 시작 → SESSION-LOCK.md 읽기
2. 자기 역할 파악 → 가이드 문서 읽기
3. Lock 걸기 → 작업 시작
4. 완료 → Lock 해제, 다음 세션 Ready
```

**실제 검증:**

우리는 이 시스템을 실제로 테스트했다:

1. **Session 1 시뮬레이션**:
   ```
   Session 1: development-log/CLAUDE.md 읽음
   Session 1: "[긴급] Act 2 개선" 발견
   Session 1: SESSION-LOCK.md 읽음
   Session 1: "나는 Session 1입니다. Act 2 개선 작업을 담당합니다."
   Session 1: ACT2-FEEDBACK-AND-GUIDE.md 읽음
   Session 1: "빠른 참조를 보니 순서 문제, 내용 누락이 있네요."
   Session 1: 바로 작업 시작 가능! ✅
   ```

2. **Session 3 시뮬레이션**:
   ```
   Session 3: SESSION-LOCK.md 읽음
   Session 3: "Status: ⏳ Waiting"
   Session 3: "Waiting for: Session 1 (Act 2 완료 필요)"
   Session 3: "Reason: Act 2 기본 개념 → Act 3 고급 전략 순서"
   Session 3 → User: "Session 1 완료 기다릴까요?
                     아니면 Act 4 draft 먼저 할까요?"
   ✅ Waiting 이유 명확, 대안 제시 가능
   ```

3. **Conflict 방지**:
   ```
   Session 2: index.html 수정하려고 함
   Session 2: 주석 발견 "⚠️ LOCKED by Session 1"
   Session 2: SESSION-LOCK.md 확인
   Session 2: "Session 1이 Working 상태"
   Session 2 → User: "Act 2는 Session 1이 작업 중입니다.
                     다른 작업(Development log)을 할까요?"
   ✅ Conflict 사전 방지 성공
   ```

**결과:**
- ✅ 세션 정체성 자동 파악: "너는 Session X" 안 해도 됨
- ✅ Conflict 원천 방지: Lock 시스템으로 충돌 없음
- ✅ 작업 순서 자동 관리: Queue로 의존성 명확
- ✅ 독립적 작업 가능: 각 세션이 가이드 읽고 자율 작업

**발견된 문제:**
- SESSION-LOCK.md의 line 범위 오류 (84-313 → 84-715)
  → 검증 중 발견하고 즉시 수정

**배운 점:**

1. **Lock 시스템의 핵심은 "발견 가능성"**:
   - CLAUDE.md에 최우선 항목
   - index.html에 주석
   - SESSION-LOCK.md에 명확한 Identity
   → 여러 경로로 세션이 자기 역할을 발견

2. **작업 가이드는 "실행 가능해야"**:
   - 추상적 지시 ❌
   - 구체적 HTML 예시 ✅
   - 체크리스트로 진행 확인 ✅

3. **검증이 중요**:
   - 시스템 만들고 끝 ❌
   - 실제 시뮬레이션 ✅
   - 문제 발견 및 수정 ✅

**⚠️ 주의:**
> "2개 세션에 Lock 시스템 = 오버킬
> 5개 이상 세션에 CLAUDE.md 섹션 = 부족
> 세션 수와 복잡도에 맞게"

**언제 이 패턴을 사용하는가:**
- 3개 이상 세션이 동시에 작업
- 같은 파일의 다른 부분 수정 (index.html Act 2 vs Act 3)
- 작업 순서 의존성 있음 (A 완료 → B 시작)
- 각 세션이 독립적으로 작업하길 원함

**대안이 더 나은 경우:**
- 2개 세션 → CLAUDE.md에 간단히 기록
- 완전히 독립적 파일 → Lock 불필요
- 순차 작업 → 한 세션에서 전부

## 📊 도구별 활용 가이드

**효과적 사용**:
```
✅ 전체 읽기: Read outline.md
✅ 부분 읽기: Read outline.md (offset=100, limit=50)
```

**팁**: Claude가 "파일을 읽어야 수정할 수 있다"고 하면, 먼저 Read 허용

### Edit 도구
**언제**: 기존 파일의 일부 수정

**주의사항**:
- `old_string`은 파일에 **정확히 존재**해야 함
- 라인 번호 프리픽스는 포함 안 함

**효과적 사용**:
```
✅ 명확한 교체:
   old: "## Act 4: Value"
   new: "## Act 4: Value (의사결정 훈련 도구)"
```

---

### Write 도구
**언제**: 새 파일 생성 또는 전체 덮어쓰기

**효과적 사용**:
```
✅ 요약 파일 저장:
   "이 분석을 sources/summary.md에 저장해줘"

✅ 개발 로그:
   "지금까지 작업 과정을 development-log/에 기록해줘"

✅ 대량 파일 생성 (SVG, 이미지 등):
```

## 🎨 설계 철학: 트레이드오프와 균형

### 정답은 없다

소프트웨어 설계에서 "무조건 이게 좋다"는 없습니다.
(있다면 그건 설계가 잘못된 것)

모든 선택은 **트레이드오프**:

```
빠른 개발 ↔ 안정성
간단함 ↔ 확장성
완벽한 설계 ↔ 빠른 실행
문서화 ↔ 프로덕트 개발
```

### 가치에 따라 선택하라

**당신의 프로젝트에서 가장 중요한 것은?**

시간이 가장 중요하다면:
- 빠른 프로토타입
- 구두 소통
- 최소한의 문서

퀄리티가 가장 중요하다면:
- 상세한 기획
- 체크리스트 검증
- 충분한 문서화

확장성이 가장 중요하다면:
- 의존성 문서
- 정식 구조
- 팀 협업 고려

### 과잉 vs 과소

```
과소 설계 ←------ 적절 ------→ 과잉 설계
(혼돈)            (균형)          (경직)

없다            필요한 것만        모든 것
빠름            적당히            느림
유연            유연              경직
혼란 위험        균형              완성 실패
```

**과잉 엔지니어링의 함정:**

장점:
- 든든함
- 확장성
- 미래 대비

단점:
1. 시간 낭비 (본질 작업 < 관리)
2. 유지보수 부담 (outdated 문서 = 혼란)
3. 인지 부담 (문서 너무 많음)
4. 변경 저항성 (바꾸기 귀찮아짐)
5. YAGNI (You Ain't Gonna Need It)

**핵심 원칙:**

> **"필요할 때 추가하기 (Just-in-Time).**
> **미리 완벽하게 만들려 하지 말기."**

### 점진적 추가 (Just-in-Time)

```
[시작]
최소한만 (README + CLAUDE.md)
    ↓
[문제 발생]
"어? 자꾸 이 실수를 하네"
→ 간단한 메모 추가
    ↓
[문제 반복]
"여러 번 까먹었네"
→ 체크리스트로 정리
    ↓
[팀 확장]
"새 사람이 이해 못 하네"
→ 그때 정식 문서
```

### 메타 설계의 역설

이 프로젝트는 이중 목적:

```
1차: 홀덤 프레젠테이션 (프로덕트)
2차: 만드는 방법 문서화 (방법론) ← 진짜 목적
```

**아이러니:**
- 프로덕트는 간단해야
- 방법론은 복잡해짐
- 본말전도?

**아니다! 평가 기준이 다르다:**

| 레벨 | 목표 | 기준 |
|------|------|------|
| 프로덕트 | 홀덤 프레젠테이션 | 빠르게, 간단하게 (YAGNI) |
| 방법론 | Claude Code 사용법 | 재사용성, 체계성 |
| 메타 방법론 | 방법론 만들기 | 균형, 실용성 |

**핵심:**
> **"프로덕트와 방법론은 다른 기준.**
> **프로덕트: 빠르고 간단하게.**
> **방법론: 깊고 체계적으로 (재사용 가치).**
> **메타: 적당히 (무한 재귀 주의)"**

### "안 이뻐서" vs "목적에 안 맞아서"

설계가 바뀌는 이유:

**표면적:**
"중앙에 큰 텍스트 이거 진짜 개구리다" = 안 이뻐서 (미적)

**실제:**
"스크립트 중심이어야 하는데 슬라이드 중심이야" = 목적 불일치 (기능적)

**어디서 잘못?**

1. 초기 설계에서 "목적" 불명확
   - "프레젠테이션" = 모호
   - 성공 기준 정의 안 함

2. 프로토타입 없이 full 구현
   - 방향 검증 스킵

**올바른 프로세스:**

```
0. 목적 명확화
   "누가, 왜, 어떻게 사용?"
   "성공하면 어떤 모습?"

1. 성공 기준 정의
   "이렇게 되면 OK" (체크리스트)

2. 작은 프로토타입
   "방향 맞나 빠르게 검증"

3. 피드백
   "목적/기준에 맞나?"

4. Full 구현
```

**설계 변경 자체는 OK:**

타당한 이유:
- 요구사항 명확화 (처음엔 몰랐던 것)
- 구현 중 제약 발견
- 더 나은 방법 발견 (창발적)

문제있는 이유:
- 막연한 불만 ("그냥 맘에 안 들어서")
- 초기 설계 부실
- 목적 불명

**핵심:**
> **"설계가 바뀌는 게 문제가 아니라,**
> **'왜' 바뀌는지 모르고 바꾸는 게 문제"**

### 실전 체크리스트

**프로젝트 시작 전:**
- [ ] 목적이 한 문장으로 설명 가능한가?
- [ ] 성공 기준 3개 말할 수 있나?
- [ ] 가장 중요한 가치는? (시간/퀄리티/확장성)

**첫 구현 전:**
- [ ] 작은 샘플로 방향 검증했나?
- [ ] "이게 목적에 맞나?" 물어봤나?

**관리 체계 추가 시:**
- [ ] 지금 당장 필요한가?
- [ ] 문제가 실제로 발생했나?
- [ ] 유지보수할 자신 있나?
- NO가 하나라도 → 나중에

**설계 변경 시:**
- [ ] "왜 바꾸는가?" 명확한가?
- [ ] "맘에 안 들어서" < "목적 X를 위해서"

- Session 1 작업 완료 후 → 실제 사용 후 개선
- 사용자 피드백 ("룰북 파일 이랑 실제 LOCK을 관리하는 파일은 따로 둬야")

**아니었다면?**:
- 처음부터 3파일 만들었을지도 → 오버엔지니어링
- 사용해보고 문제 발견 → 실용적 개선

**패턴:**
> **"일단 써보고 → 문제 발견하면 → 그때 개선"**

**3. Redirect 파일의 가치**

**SESSION-LOCK.md를 삭제 안 하고 redirect로:**
- 기존 문서/링크 깨지지 않음
- "왜 변경했는지" 설명 가능
- Git history 보존

**만약 삭제했다면?**:
- 다른 세션이 SESSION-LOCK.md 찾다가 혼란
- 링크 깨짐

**패턴:**
> **"중요 파일 이동 시 redirect 남기기"**

**4. 완료 체크리스트의 진화**

**SESSION-RULES.md의 강화된 체크리스트**:
```markdown
### ⚠️ 작업 완료 후 (반드시 확인!)

- [ ] 1. 최종 commit & push
- [ ] 2. 작업 가이드 문서 변환 (있는 경우)
- [ ] 3. SESSION-STATE.md 업데이트
- [ ] 4. Blocking하던 세션에 알림

**⚠️ 위 4단계 모두 완료하지 않으면 다음 세션이 시작 못합니다!**
```

**개선점**:
- "Optional"이 아니라 전부 필수화
- Session 1이 #2를 Optional로 남겨둔 문제 → 규칙에서 명시
- 경고 문구로 중요성 강조

#### 실전 활용

**언제 분리할까?**

**분리해야:**
- ✅ 변경 빈도가 10배 이상 차이
- ✅ 한 쪽 수정 시 다른 쪽 건드릴 위험
- ✅ 책임이 명확히 다름

**분리 안 해도 됨:**
- ❌ 아직 작은 파일 (<100 lines)
- ❌ 변경 빈도 비슷
- ❌ 항상 같이 읽음

**SESSION-LOCK 사례:**
- ✅ 규칙 vs 상태 (변경 빈도 차이 큼)
- ✅ 실수로 규칙 수정 위험
- ✅ 300+ 줄로 길어짐

**리팩토링 타이밍:**
- Pattern 10으로 검증 완료
- Session 1 실제 사용 후
- 사용자가 문제 지적

> **"Premature optimization is the root of all evil"**
> 하지만 **"문제 생긴 후 개선은 당연"**
